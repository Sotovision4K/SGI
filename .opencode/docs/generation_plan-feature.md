# Plan Generation Feature

Endpoint + background worker that turns a completed diagnosis into a certified action plan.

## 0. Current state (as-is)

- One synchronous endpoint `POST /processes/{id}/generate-plan` (`backend/src/routes/processes/routes.py`), one adapter `AnthropicAdapter` (`backend/src/adapters/llm/anthropic_adapter.py`) via the `LLMPort` protocol, `max_tokens=4096`, tool-use `emit_action_plan`.
- Result is persisted on success: `replace_plan` → `plans` + `tasks` tables → status `PLAN_READY`; read back via `GET /plan`. `replace_plan` also serves as the **regenerate** mechanism — it wipes any existing `plans`/`tasks` rows for the process before writing fresh ones.
- No custom error classes, no LLM logging/audit, no retries, no timeout.

> **⚠️ Phase 0 bug (fixed 2026-09-16)**: `replace_plan` accessed the committed `plan_row` after `session.commit()`. SQLAlchemy expires ORM objects on commit (`expire_on_commit=True`), so `_plan_to_domain(plan_row, …)` triggered a lazy-load refresh → async IO in a sync context → `sqlalchemy.exc.MissingGreenlet` (seen in production Lambda logs). Fixed by returning the domain `plan` directly instead of re-reading the expired row. Covered by real-DB regression tests (`tests/integration/test_replace_plan.py`, 3 tests) against an in-memory aiosqlite engine. The bug affected **both** first-generation and regenerate — every `generate-plan` call on the old code path.

## 1. Functional requirements

- The plan generation is segmented into chunks based on buckets: **Liderazgo**, **Contexto/Apoyo**, **Operación/Mejora** (see §5).
- The plan is generated by the LLM.
- Output must be parseable JSON produced by a single tool call — the LLM must return only the JSON, nothing else.
- The LLM has **not** the final answer: the user can edit the plan afterward. Keep the plan in the DB and allow re-generation (idempotent/resumable).
- On any job failure, a retry mechanism is applied (tenacity → SQS redelivery). A **retry limit** is enforced; past the limit the message goes to the **DLQ**.
- The user can trigger a retry themselves; if it fails again, no more retries are sent and an on-call engineer is expected to check it. The user is informed on screen while retrying.
- Audit of the prompt is kept in a dedicated table; structured logs are generated at the adapter, including status and the token input/output counts.
- A successful generation writes the plan, the audit records and the DB rows, capturing prompt + input tokens + output tokens.

## 2. Technical requirements

- Third-party (LLM) call timeouts are handled, logged, and surfaced to the user with a message on the frontend.
- Parsed response is **deduplicated by title normalization**.
- Custom error classes are created (rooted on `LLMError` / `PlanGenerationError`, split **retryable** vs **terminal**).
- HTTP mapping: new-path handler calls map to status codes (enqueue failure → 503, missing findings → 400, generation cap → 429, already running → 202 reuse). Existing route `HTTPException` usage is kept.
- **Consistency — snapshot at enqueue**: `POST generate-plan` copies a snapshot of `findings` + `pre_diagnosis` into the `plan_jobs` row. The worker reads **only the snapshot**, never the live DB, so a plan always reflects the diagnosis the user submitted (fixes the stale-data race).
- **Ownership — `consultant_id` binding**: `plan_jobs` snapshots `consultant_id` at enqueue. The worker re-verifies ownership on **every** call: it compares the SQS message's `consultant_id` against the job's snapshot and rejects any mismatch. The authorization decision is made once in the authenticated enqueue route, then sealed into the message — SQS has no user identity, so the worker must not "trust the job origin" blindly.
- **Duplicate-safety — claim guard**: the worker atomically flips `queued → running` (`UPDATE … WHERE status='queued' AND consultant_id = :consultant_id`). Only the first winner proceeds; duplicate/redelivered SQS messages give up without re-cooking or repeat token spend. The frontend loader additionally blocks double-clicks.
- **Generation limit**: **hard cap of 3 per process** (no per-user/monthly cap). **Only `completed` jobs count** — failed/running/queued don't burn an attempt. Enforced at enqueue → `429`.
- **Segmentation map (JSON)**: `questionnaire_map.json` drives both the bucket split (question → group → bucket) and the Spanish prompt labels via `.format()`. The DB stores answers in **English** as entered; the prompt-building layer maps each answer to Spanish. Single source of truth for bucketing + localisation.
- **Editable plan**: the user can edit tasks afterward. `PUT /processes/{id}/plan/tasks/{task_id}` updates a single task (ownership + task-belonging checked) and bumps the plan's `updated_at` + a revision marker so generated vs hand-edited plans are distinguishable.
- **Notification on completion**: in-app only (via `status` polling → banner/toast). Slack push is **deferred** (Technical Debt).

## 3. Architecture

```
POST /processes/{id}/generate-plan   (auth + rate-limit + cap→429 + idempotency 202 reuse)
   → snapshot findings+pre_diagnosis → create plan_jobs row (queued) → one SQS message → 202 {job_id}
SQS  ──event source mapping──► same Lambda (handler.py branches on aws:sqs)
worker run_plan_generation(process_id, consultant_id):
   verify consultant_id == job.consultant_id (reject mismatch — terminal, no retry)
   claim: atomic queued→running WHERE status='queued' AND consultant_id=:cid (loser gives up)
   read plan_jobs snapshot (NEVER live DB)
   split answers → 3 buckets (questionnaire_map.json: group→bucket; shared across standards)
   shared context → all 3 buckets; labeled Q&A (Spanish via .format on map) + scope boundary → each bucket
   asyncio.gather(3) + Semaphore(3) + tenacity retry + per-call timeout + max_tokens≈1500
   checkpoint each bucket into plan_jobs.segments; in-memory second-pass retry of failed bucket
   all done → merge summaries + dedupe tasks (title) + re-stamp sort_order → single replace_plan → PLAN_READY, completed_count+1
   past retry cap → job failed + error (DLQ message + CloudWatch alarm)
   + structured log + audit_logs_llm row per call (usage/latency/status)
frontend polls GET /plan-generation/status  until completed → GET /plan (loader blocks edits while running)
PUT /processes/{id}/plan/tasks/{task_id}  → edit one task; bump updated_at + revision marker
```

### Reuse (no new Lambda)

The queue triggers the **same** `aws_lambda_function.api`; `handler.py` branches on event shape (`aws:sqs` → worker, else Mangum). Ownership is **enforced at enqueue** (authenticated route) and **re-verified at claim** (`consultant_id` binding) — the worker does *not* blindly trust the job origin.

## 5. Segments & LLM context

| Bucket                | Questionnaire groups             | ISO clauses    | ~questions* |
| --------------------- | -------------------------------- | -------------- | ---------- |
| B1 Liderazgo          | `liderazgo`                      | 5.1–5.3        | 3          |
| B2 Contexto y Apoyo   | `contexto, planificacion, apoyo` | 4.x, 6.x, 7.x  | 9          |
| B3 Operación y Mejora | `operacion, evaluacion, mejora`  | 8.x, 9.x, 10.x | 12         |

\* **Counts are NOT fixed** — they follow the actual `questionnaire_map.json` per standard (iso9001=24 questions; iso14001 & iso45001=21). Bucket size is derived, never hardcoded. The grouping (`groups` → `bucket`) lives in the map config.

Each call receives: **shared** (company name, ISO, full pre-diagnosis, full free_text, certification goal, data-not-instructions banner) + **bucket-local** (labeled Q&A with clause + question text, own clause list, "tasks only for your clauses"). Localised to Spanish via the map's `es_label` using `.format()`; DB stays English. Sanitized before sending.

**Merge** (in code): `summary_md` = segment summaries joined with markdown headers; `tasks` = concatenated, deduplicated by normalized title, re-stamped `sort_order`.

## 6. Data model (new tables)

Both auto-created by `create_all` on cold start — no migration needed.

**`plan_jobs`**: `process_id` (PK, FK→processes), **`consultant_id`** (indexed; owner snapshot — ownership re-verified on every worker call), `status` (queued/running/completed/failed), `error`, `segments` (JSONB per-bucket status/tasks/summary/error), `failed_attempts`, **`findings_snapshot`** (JSONB, snapshot at enqueue), **`pre_diagnosis_snapshot`** (JSONB), **`source_updated_at`** (findings timestamp at enqueue), **`completed_count`** (counts successful generations for the cap), `created_at`, `updated_at`.

**`audit_logs_llm`**: `id` PK, `process_id` FK, `job_id`, `bucket`, `attempt`, `model`, `iso_standard`, `request_payload` (JSONB sanitized), `response_json` (JSONB sanitized), `input_tokens`, `output_tokens`, `latency_ms`, `status`, `error`, `created_at`.

**Entity additions** (`plan.py` / `plan_tool.json`): `Task.source_clause` (string, filled from bucket), `Task.require_document` (bool, default false), `Task.document_title` (nullable).

### Entity vs. DB metadata separation

The domain entity (`Task`, `Plan`, `Finding`) is the business model — what the LLM produces, what the frontend consumes, what business logic operates on. The SQLModel table (`TaskTable`, `PlanTable`) is the persistence model — it may carry extra columns for DB concerns that are never promoted to the entity.

| Column | On table? | On entity? | Why |
|---|---|---|---|
| `source_clause` | ✅ | ✅ | Domain — server-filled clause per task |
| `require_document` | ✅ | ✅ | Domain — LLM output |
| `document_title` | ✅ | ✅ | Domain — LLM output |
| `updated_at` | ✅ | ❌ | DB metadata — bumped by `PUT /tasks/{id}` route handler; never consumed by consumers of `Task` |
| `document_url` | ✅ | ❌ | DB metadata — set by file-upload route; never consumed by consumers of `Task` |
| `user_id` | ❌ | ❌ | Auth concern — lives on `Process.consultant_id`, not on tasks |
| `llm_client` | ❌ | ❌ | Audit concern — lives on `AuditLogLlmTable.model` |

**Exception**: `Finding.updated_at` IS on the entity because `GET /findings` exposes it to the frontend. Unlike `Task.updated_at`, it's consumer-facing. The mapper passes the DB value correctly (fixed 2026-08-09: `_finding_to_domain` was previously dropping it, causing a factory-default mismatch).

## 7. Retry & failure handling

Ladder:

1. **tenacity** (exp backoff + jitter + per-call timeout) — transient LLM errors.
2. **SQS visibility timeout** (~300s) + event source mapping `maximum_retry_attempts`.
3. **Queue redrive → DLQ** — terminal; message preserved for inspection/replay.

Semantics: `RetryableError` (rate-limit, service, timeout, connection, tool-not-emitted) → retry, then DLQ. `TerminalError` (format, rejected, findings missing) → fail job immediately, no retry. Recovery: DLQ CloudWatch alarm → SNS; user "Retry" resumes only the failed buckets via the checkpoint.

## 8. Observability

- Structured CloudWatch logs per call (correlation id = process+job+bucket) and per merge.
- `audit_logs_llm` rows on every call (incl. retries): sanitized prompt/response + `usage` + `latency_ms` + `status`.
- `AuditLogWriteError` never breaks generation (log + swallow).

## 11. Compact decisions, concerns & open questions

### Decisions

1. **Async SQS + Lambda** (same function, handler branch); `POST` enqueues one message per process, returns idempotent `202` (reuses existing job while queued/running).
2. **3 buckets** (Liderazgo / Contexto+Apoyo / Operación+Mejora), group→bucket map in `questionnaire_map.json`; shared context + labelled Q&A + scope boundary; **merge in code** (no 4th LLM call).
3. **Resumable checkpoint** (`plan_jobs.segments`): retries and "Reintentar" re-run only the failed buckets.
4. **Fail-closed UX**: partial plan never persisted; plan tables written only on full success (previous plan preserved).
5. **Retry ladder + DLQ + CloudWatch alarm → SNS**; terminal after limit → job `failed` + operator review.
6. **Observability**: structured logs + `audit_logs_llm` (sanitized payload + tokens + latency); audit failures never break generation.
7. **Error taxonomy**: `RetryableError` vs `TerminalError` root; tool-not-emitted = retryable.
8. **Same Lambda, reuse adapter** — no new infrastructure function; `_require_process_owner` stays at the API layer.
9. **No migration** — new tables/columns via `create_all`.
10. **OpenCode reusables**: `/adr` command added; future `/adr` command can compact any design session.
11. **Consistency — snapshot at enqueue**: worker uses the `plan_jobs` snapshot (never the live DB).
12. **Duplicate-safety — claim guard**: atomic `queued→running` via `UPDATE … WHERE status='queued' AND consultant_id=:cid`; duplicate/redelivered messages give up (no repeat token spend). Frontend loader also blocks double-clicks and edits while running.
13. **Ownership — `consultant_id` binding**: the SQS message carries `consultant_id`; the worker rejects any message whose value doesn't match the job's snapshot. No `run_token` — `status='queued'` alone is sufficient for atomicity.
14. **Generation limit**: **hard cap of 3 per process** (no per-user/monthly cap); **only `completed` jobs count**; enforced at enqueue → `429`.
15. **Single segmentation/localisation config (`questionnaire_map.json`)**: drives bucket split and Spanish prompt labels via `.format()`; **DB stores English**.

### Cost/trade-offs

- SQS ≈ **$0.10/mo** (vs Procrastinate `$8–9/mo` + always-on worker); Supabase cannot host a Python worker.
- Fan-out ≈ **2–2.5×** LLM input tokens of current, acceptance 2–2.5× the price of parallelism.

### Concerns / risks

1. **B3 slowest critical path** (per-standard size; ~12 q on iso9001) — mitigated by task cap + bounded retries; may exceed 15s worst case. Set Lambda timeout + SQS visibility to worst-case attempt+backoff.
2. **Cross-bucket coherence** — fan-out limits global priority; mitigated by shared context + scope boundary + dedupe.
3. **Same-Lambda concurrency** — jobs could contend with interactive API; later reserved concurrency.
4. **DLQ is terminal** (manual replay only via "Reintentar"); alarm ensures visibility.
5. **Incremental `segments` writes + LLM payload storage** — sanitize + retention cleanup; failures never touch plan tables.
6. **Cap-tuning** — hard cap `3` per process; revisit only if product wants more attempts (only `completed` counts).

### Open questions

1. ~~**Entity field changes under §8**~~ — **RESOLVED**: add `require_document`, `document_title` to entity; `source_clause` server-filled; `updated_at`/`document_url`/`user_id`/`llm_client` are metadata only.
2. ~~DLQ redrive~~ — **RESOLVED**: **manual "Reintentar" only**; no auto redrive.
3. ~~Completion notification~~ — **RESOLVED**: **in-app only** via polling; Slack push deferred to a future streaming agent (Technical Debt).
4. ~~Extract fan-out + audit as reusable modules~~ — **DEFERRED**: do it on the **next** LLM feature.

### Technical debt (not in scope now)

- **Streaming agent → Slack** on plan completion. Adds an always-relevant feed of generations; pull it in if/when multi-user notifications become a need.
- **Fan-out + audit as reusable modules** — decouple from `plan_generation` before the next LLM feature touches this code.
